# T-0210 UI syntax and generated-output guards

`make ui-check` runs tools/check_tokens.py and tools/check_strings.py.
`make theme-check` runs tools/check_theme.py with the selected GODOT binary.
Both run in `make check`; CI runs one extra UI-guards job and requires it before
Android debug APK/release inspection. Existing checks, credentials and exports remain intact.

The syntax guards use the installed gdtoolkit/Lark parser, not line-based GDScript grep.
Scope is game/features/** and game/ui/components/**, *.gd and *.tscn. Comments and
strings containing code are not parsed as code. Missing scan roots, script parse errors,
malformed scene properties and a missing/empty locale catalogue fail. Diagnostics contain
relative paths, source lines and R-UI-3/R-UI-4. No file or line allowlist is used.

Token checks cover direct literal colours/hex strings, tween durations and numeric theme
font/constant overrides or known visual properties. Tokens plus dynamic alpha, dynamic
insets, neutral layout 0/1/-1 and identity Color.WHITE remain valid. Scene arrays may span
lines; serialized colours and positive durations must still be token-driven in scripts.

Copy checks cover common text/tooltip/placeholder/accessibility assignments and drawing,
setter/list/tab calls. Translation keys and ProjectSettings.get_setting's property path
are metadata; defaults or concatenated literal words still count as copy. Empty strings,
punctuation and printf/numeric format-only strings are valid. Literal tr keys and static
scene text keys are checked against per-area locale CSV keys.

These are bounded syntax guards: dynamic gameplay letters/words are valid. They do not
perform interprocedural dataflow analysis, infer widget types or prove dynamic values
originate from tokens/translations. Unlisted setters/properties and values passed through
variables still need code review. This does not promise full semantic Godot scene validation;
Godot import remains a separate mandatory check. Later UI APIs should extend the guarded
sinks with regression tests rather than adding suppression lists.

Theme freshness copies the project into a temporary directory without .godot cache,
imports with the pinned engine and invokes the existing generator. It compares all 14
outputs: six theme variants, Inter.res, five FontVariations, font licence and CSS mirror.
Missing files, byte drift, engine errors/warnings and timeout fail. The source project is
never regenerated by the check, including on failure. To update deliberately, import
and run the documented theme generator, then review/commit changed outputs.

Verification: real-engine clean-cache comparison PASS; an actual theme hand-edit in a
separate source fixture was rejected with the output path/regeneration command, and its
bytes remained unchanged. Unit tests cover all 14 output paths, matching/missing/drift,
engine failures/warnings and nonmutation, plus AST/scenes/scope/CLI cases. Full make check,
independent review and final-head CI evidence are recorded in the PR.

The earlier runtime/asset stack must merge first. No runtime, save, economy, theme generator,
font source, signing/permissions or ROADMAP changes. Previous manual gates stay open.
